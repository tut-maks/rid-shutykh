# Рід Шутих — закритий родинний архів

Дерево роду, гілки-родини з історіями, картки людей з архівними документами, фото і спогадами.
Родичі заходять лише за запрошенням; власник бачить аналітику (хто що дивився і скільки часу) та історію всіх змін з відкатом.

## Як влаштовано (і чому це безпечно)

```
Браузер ──► лише /api/* на нашому домені (cookie HttpOnly, Secure, SameSite)
               │
               ▼
        Vercel-функції (api/*.js) — перевіряють сесію і права на КОЖЕН запит
               │ ключ service_role (лише змінна середовища Vercel)
               ▼
        Supabase: Postgres (RLS увімкнено, політик немає → ззовні нічого не видно)
                  Storage «family» (закритий; файли віддає тільки наш сервер)
```

- **Браузер не має доступу до бази взагалі.** На сторінці немає ключів Supabase. Навіть якщо хтось дізнається адресу проєкту Supabase, без ключа service_role він нічого не прочитає: RLS увімкнено, а політик доступу немає.
- **Фото й скани** зберігаються в закритому сховищі. Їх віддає функція `/api/file` і лише тому, хто увійшов, тож прямих посилань, якими можна поділитися, немає.
- **Вхід.** Пароль зберігається як хеш scrypt. Сесія — випадковий токен у cookie `__Host-…` з позначками HttpOnly і Secure, у базі лежить лише його хеш. Кількість спроб входу обмежена.
- **Запрошення** одноразові й діють 7 днів, у базі зберігається лише хеш токена. Скидання пароля робить власник новим посиланням, і всі старі сесії при цьому закриваються.
- **Захист від підробки запитів:** зміни приймаються лише з нашого домену (`Sec-Fetch-Site` / `Origin`).
- **Заголовки:** суворий CSP (скрипти лише з нашого домену), заборона вбудовування в iframe, HSTS, noindex.
- **Ролі:**
  - власник — усе, аналітика, доступи, відкат змін;
  - редактор — додає й змінює картки, фото, історії родин;
  - глядач — дивиться і пише спогади.
- **Журнали:** кожна зміна записується в `revisions` (що було → що стало, хто, коли), перегляди — в `events`.

## Розгортання — покроково

### 1. Supabase
1. supabase.com → **New project** → назва `rid-shutykh`, регіон **Frankfurt**.
2. **SQL Editor → New query** → вставити весь файл `supabase/migrations/001_init.sql` → **Run** (має бути «Success»).
3. **Project Settings → API** → скопіювати **Project URL** і ключ **service_role** (секретний).
4. **Authentication** не потрібна: вхід реалізовано на нашому сервері.

### 2. Vercel
1. vercel.com → **Add New → Project** → імпортувати репозиторій `rid-shutykh`.
2. Framework Preset: **Other**, Build Command порожньо, Output Directory `public`.
3. **Settings → Environment Variables:**

| Змінна | Значення |
|---|---|
| `SUPABASE_URL` | Project URL із Supabase |
| `SUPABASE_SERVICE_ROLE_KEY` | ключ service_role (**секретний**, ніде більше не вставляти) |
| `BOOTSTRAP_TOKEN` | довгий випадковий рядок, одноразовий код для створення власника |

4. **Deploy.**

### 3. Перший запуск
1. Відкрити сайт → «Перше налаштування» → ввести `BOOTSTRAP_TOKEN`, ім'я, пошту, пароль (від 10 символів).
2. Натиснути **«Імпортувати»**: у базу завантажаться дерево, родини і скани (з папки `seed/`).
3. **Власнику → Доступи** → запрошувати родичів. Посилання надсилати особисто.
4. Після першого входу `BOOTSTRAP_TOKEN` можна видалити з Vercel: повторно створити власника вже не вийде.

### 4. Домен
Vercel → Project → Settings → Domains → додати домен → у DNS домену прописати записи, які покаже Vercel.

## Локальна перевірка
`npm run dev` → http://localhost:3000. Працює без Supabase: база в пам'яті / файлі `/tmp/rid-shutykh.mock.json`, код налаштування `dev-bootstrap-token`.

## Структура
- `public/` — сторінка (`index.html`, `app.js`, `app.css`), без збірки.
- `api/` — серверні функції: `auth` (вхід, запрошення), `data` (дерево і зміни), `file` (віддача файлів), `upload` (фото), `track` (аналітика), `admin` (панель власника), `setup` (перше налаштування).
- `api/_db.js` — єдине місце звернення до бази і сховища.
- `supabase/migrations/` — схема бази.
- `seed/` — початкові дані й скани (імпортуються один раз).
